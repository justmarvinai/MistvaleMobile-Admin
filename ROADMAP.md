# Mistvale Admin Suite — Roadmap

> Phases here are **locked in step with the game repo's roadmap** (`MistvaleMobile/ROADMAP.md`, phases P0–P10). Rule: whenever a game phase introduces a content table, its editor ships in the _same_ game phase — content authoring is never blocked on the suite lagging behind. Each phase ends with a feedback checkpoint (owner is invited — never required — to request changes/bugfixes).

**Post-EA (parked):** guild tooling, Mistspire/Doom-Tower editor, fusion event designer, TOTP for admin accounts. Three came off this list rather than being built: **faction trials** were dropped outright (game repo, 2026-08-27), the **battle pass** shipped as the Vale Pass with its own reviewing page (game repo C38 — a season's _length against its schedule_ is the figure the generic browser cannot show), and a **localization editor** is moot for as long as content is English-only, which is what the owner settled in Q10 (2026-08-30). If a second language is ever wanted, the locale dimension on `content_entries` is the game repo's migration and the editor follows it rather than leading.

**Definition of Done per phase:** editors cover every field of their tables (no "edit it in SQL" gaps) · publish validation blocks every referential break the docs specify · audit entries for every mutation · Vitest coverage on composer/diff logic · CHANGELOG updated · feedback checkpoint offered to the owner.

### Where the suite stands

**A0–A4 complete, A5 all but closed, and the smoke run in. The game repo has finished P0–P10, closed its design rework and is deep into the owner's change batches**, so what is left here is **A6**'s asset manager and three A5 items that each need something that does not exist yet.

**A2 closed with one item cut rather than built.** §2.9's drop-table editor described a generalised `dropTable` content type that was never made: a stage carries its own drops band inline, which is what makes a chapter a farm for one specific thing, and the `dropTableKey` field left over from the original plan was declared in the schema and read _nowhere_ (removed in the game repo's C34). What A2 shipped instead is the two views that had no substitute — the **campaign grid** and the **battle inspector**. The **balance sandbox** arrived ahead of both (game repo C27) and stays at **Live ops → Balance sandbox**: it is a question rather than an edit, and wiring it into a stage editor is a link rather than a rebuild.

**A3 closed with all five of its items.** The **summon pool** and **shop** screens are the same argument twice — every field of both is already editable in the generic browser, and neither says what a number _does_. The **publish center** has carried draft → validate → diff → publish → revert since A1. The **gear upgrade tables** are curves in the config editor rather than JSON blobs. And **export/import** lives inside the publish center rather than beside it, because §2.17 asks that an import show a dry run first and an import writes _drafts_ — so the dry run is the publish center's own field-level diff, one click away, rather than a second review path that would need its own trust.

**A4 closed as four reviewing views**, and the shape they share is the argument for building them at all: every one of these content families was _already_ fully editable in the generic browser, so none of them was blocked — what none of them could show is the **shape a set of entities adds up to**. A keep is fifteen stage rows in a list of four hundred; a mastery board is forty-eight rows whose effects are a nested union; a login track is thirty days inside one array; the Path is eighty missions walked by a number that a key-ordered list scatters. Each screen also names the faults that publish cleanly and are invisible in a form — a descent that gets _easier_, a board no pair of trees can fill, a gap in the Path's numbering, a ladder whose rungs do not climb, a window that ends before it starts.

Two things A4 sketched were deliberately **not** built, both for the same reason: the data does not support them. The mastery **node canvas** would draw prerequisite edges, and Mistvale's board has none — the gating is arithmetic over tiers and picks. The **goal-DSL builder** and drag re-ordering are the tutorial editor's argument again: field editing stays in the generic browser, which is schema-driven and complete, and re-ordering earns a purpose-built control only where publish _refuses_ a numbering fault. Today the Path reports one instead.

**The bot manager shipped with the game repo's P7** (§2.15): a ladder view by band, and the two actions a config edit cannot perform by itself — fill to strength, and rebuild now. Everything tunable about a band stays in the Game config editor rather than being mirrored here, and an individual bot is managed through Players like any other account, because a bot _is_ an ordinary player row. Only the "bot density vs real players" health check is deferred, since it needs a real population to mean anything.

**The smoke run closes G8.** `pnpm e2e` drives sign in → edit → diff → validate → publish → read the change back through `/api/content`, plus a walk of every screen and every content type by clicking the sidebar. It is not part of `pnpm verify`, because it needs the game server, this SPA and an admin account all running — and it **cannot mint that account**, deliberately: there is no self-serve promotion and there must not be, so the first admin on any box is made with the game repo's `SET_RANK.sh` and the credentials come in as environment variables. That is what keeps this repo's hardest rule intact while still testing the whole chain.

**A5 is closed but for three items, and each is blocked on something rather than merely unbuilt.** Shipped: search, the account page, six audited actions, the **fresh-start reset**, the **holdings drill-ins** (roster, vault, pull history) and **Jobs & health**. Still owed: battle history linked into the inspector (a query the inspector does not take yet), grants of champions and gear rolls (a roll is content-shaped and wants the reward picker to grow), and bulk actions (the composer takes a target, not a result set).

The drill-ins are worth a note about what they deliberately are **not**. There is no button on that card that changes anything, and that is the design: every change to what an account holds already exists as a grant, which lands in `economy_log`. A control there would be the one mutation in the suite with no ledger behind it. The reads are not audited either, for the balance sandbox's reason.

**Player management jumped the queue**, and the reason is worth recording: Mistvale has no e-mail addresses anywhere, so an operator is the _only_ password reset that exists — and there was no operator endpoint. That is a hard-rule violation rather than a missing convenience, so search, the account page and six audited actions (reset password, set rank, ban/unban, rename, grant, sign out everywhere) shipped ahead of A2. The rest of §2.14 — roster and gear drill-ins, summon history, gift-mail attachments, bulk actions — stays at A5 where it belongs, since all of it needs systems that do not exist yet.

The lockstep rule — _whenever a game phase introduces a content table, its editor ships in the same game phase_ — held in the sense that matters: P6's two new content families (`dungeon`, `mastery`) are **fully editable today** through the generic entity browser, which is schema-driven and covers all 20 types, so no field is SQL-only and nothing about authoring the Depths or a mastery tree is blocked. What is still owed is the _purpose-built_ editing they were promised — a floor-band view for a dungeon, a tree canvas for masteries — and those stay scheduled at A4.

The scale A2 has to design for is now real rather than hypothetical: **409 stages** are published — 252 campaign across 12 chapters × 3 difficulties, 120 Depths floors, the Mistspire's 30, four Trials, the tutorial's cold open, one Titan run and one world-boss strike. The campaign and the Depths are _generated_ in the game repo's seed from twelve and ten plan entries respectively, so the campaign editor's job is reviewing and retuning generated content — a stage grid per chapter and difficulty, and a wave composer that makes a retune cheap — rather than offering to create 252 rows by hand. The Deep Run's eleven rooms are deliberately not among the 409: a room is synthesised into a stage at battle start, so the whole descent is one `deepRun` entry.
